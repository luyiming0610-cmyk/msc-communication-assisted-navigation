## The defect chain, in order

1. **`controller_v1`**: the canonical combined wooden-box + moving-peer
   scenario (`experiments/cooperative_avoidance_20260716/config/
   combined_wood_moving_peer/`) found a safety defect: after `epuck1`'s box
   bypass, a grazing IR flicker near the box's trailing corner could
   repeatedly re-arm an unbounded turn (observed: one continuous turn of
   ~4.8s / ~1.2rad), swinging the robot into the box in 3 of 4 diagnostic
   pilots and leaving only 0.0014m clearance in the fourth. Root cause: no
   cumulative-turn or re-arm-distance bound on the direction-latch bypass.
   Phase 1-3 protocols never ran long enough to hit this window, so their
   results were never affected. **Status: registered, not retracted — see
   below.**
2. **`controller_v2_local_latch_20260717`**: first fix attempt at the latch
   design. See `controller_v2_local_latch_design_20260717.md`.
3. **`controller_v3_unified_encounter_20260717`**: replaced the latch with a
   single unified encounter state machine.
4. **`controller_v4_full_sensor_bypass_20260717`**: current tip. Two
   sub-phases:
   - Initial v4 state machine (`EncounterAvoidanceV4`): fixed three more
     distinct defects found across `pilot_v4_a` attempts 1-3 (permanent
     SIDE_TRACK stall; structurally-unreachable ps-zone evidence; a single
     dropped-odometry glitch causing a bogus FAILSAFE).
   - `controller_v4_ros_time_consistency` (this session): found and fixed a
     **second, independent** defect — the controller mixed
     `time.monotonic()` and the ROS/simulation clock for motion timers,
     which `simulation_rate_integrity_audit_20260716.md` had already flagged
     as a risk in its "Engineering follow-up" section. Fixed by routing
     every such timer through `self.get_clock().now()` exclusively. Also
     redesigned the turn ledger to be command-gated (only counts a yaw delta
     as "turning" when the previous tick's actual applied angular velocity
     crosses a threshold; otherwise it's checked against a noise band and,
     if persistently exceeded, escalates to a `PERSISTENT_DRIFT` FAILSAFE).
     This ledger redesign is what actually closes the original box-corner
     runaway-turn defect: any single-direction turn now has a hard
     cumulative-radians ceiling regardless of how many times a sensor
     flickers it back into an active mode.

## Two open findings (status as of 2026-07-17, later same day)

1. **`self.started_at` clock-init race — FIXED** (`controller_v4_timebase_fix_20260717`,
   git commit `980e7d0`). Root cause confirmed: `self.started_at = self._now_s()`
   was captured in `__init__`, before the node's ROS-time clock subscription
   necessarily has its first `/clock` sample under `use_sim_time=true` (a
   known rclpy race where `Clock.now()` reads exactly `0.0` until then).
   Fixed by a new `_ensure_timebase()` method that only captures
   `started_at` on the first control tick where the clock reads a valid
   nonzero sample (the controller reports `mode=WAITING_FOR_CLOCK` and
   holds station until then), and that also detects and safely re-bases a
   backward ROS-time jump (`TIMEBASE_RESET`, e.g. a simulation reset).
   5 new tests added (96 passed total, was 91). Re-validated with a fresh
   combined-pilot regression (`combined_trial2_timebasefix`, git commit
   `06e0f0f`): `TIMEBASE_INIT` logged at each robot's real first-valid
   ros_time (18.640/19.580, not 0), `stopped_by_max_runtime_only=false`,
   verdict PASS. See `simulation_rate_integrity_audit_20260716.md`'s
   2026-07-17 addendum for the original finding.
2. **Live-vs-offline agreement not verified for `pilot_v4_c` and either
   combined-pilot run**: all three were run unattended; no human visually
   observed them. Only `pilot_v4_b3` had this kind of consideration during
   its design (early-success watcher cross-checking ground truth against
   the controller's own log). Formal Phase 4 Trial 01 will be directly
   observed by the user — use that opportunity to sanity-check this class
   of pilot too.

### Combined-scenario naming correction (do not use the old phrasing)

The combined Phase 4 scenario must be named **"staged local-obstacle
avoidance followed by communication-assisted proximity/cooperative
avoidance"**. Do not call it "synchronized" or say it is "triggered by
predicted CPA" — offline reconstruction (`analyze_trigger_reason`, git
commit `28f78d6`, read-only analysis, frozen controller untouched) confirms
the combined pilot's actual AVOID_TURN trigger was `PROXIMITY_FALLBACK`
(`current_distance<0.34m`), not `PREDICTED_CPA` (`tcpa<=4.0s and
dcpa<0.14m`): at trigger `t=54.621s`, `dcpa_at_trigger=0.211m`, well clear
of the 0.14m predicted-conflict threshold. Both trigger paths are genuine
parts of the same frozen controller
(`collision_math.collision_risk`); which one fires is a property of
approach geometry/speed at record time, not a defect, and is exclusionary
engineering evidence either way. Even `pilot_v4_c` (pure CPA, no box)
triggered via `PROXIMITY_FALLBACK`, but as a genuine near-simultaneous tie
with `PREDICTED_CPA` (full trace in
`bags/*_head_on_cpa_pure_c1/analysis/trigger_classification.csv`) — not
comparable to the combined pilot's clear proximity-only trigger.

Category 1 (pure CPA) evidence for the dissertation: `pilot_v4_c` plus the
five pre-v4 `head_on_cpa_only_trial_02..06_postfix` repetitions (2026-07-16,
`cooperative_avoidance_20260716/`) *as originally recorded and analyzed* —
those five bags cannot be re-processed by the new trigger-reason classifier
because `EpuckState.msg` gained fields since they were recorded, changing
the wire type hash (`Fast CDR exception deserializing message`); this is a
ROS2 bag/schema-versioning limitation, not a defect, and is disclosed here
rather than worked around. **`EpuckState.msg` is now formally frozen as
PROTOCOL_VERSION=1** — see
`src/epuck2_comm_interfaces/PROTOCOL_FREEZE_20260717.md` for the exact field
list, fingerprint (git blob hash + SHA-256), and the rule that no field may
be added/removed/reordered in v1 going forward (a structural change would
need a distinct PROTOCOL_VERSION=2). Those five bags are explicitly labeled
"pre-protocol-freeze legacy evidence" there: their original summaries remain
citable, but they must never be presented as v1-wire-compatible or
reprocessed through any v1-assuming analyzer.

### Webots vs. Gazebo: known, disclosed deviation from the official Spec

The Spec and SP both name Gazebo. The actual simulator used throughout this
project is **Webots R2025a**. This is a genuine, undisclosed-until-now
deviation and must be stated plainly in the dissertation, not hidden:

- The ROS2 Custom Msg protocol (`EpuckState.msg`) and the `epuck2_comm`
  library are simulator-agnostic by design — they depend only on ROS2
  topics/messages, not on which simulator publishes the underlying
  odometry/sensor data. Nothing in the protocol or library itself is
  Webots-specific.
- Webots supplies robot dynamics and sensor simulation (via
  `webots_ros2_driver`) in place of Gazebo; the `state_publisher` node
  reads the same category of topics (odometry, IR/ToF ranges) that a
  Gazebo-backed e-puck2 model would publish.
- The communication protocol and library are written to the same interface
  the physical Pi-puck will use, so switching the simulator does not by
  itself require any protocol change when moving to real hardware.
- Practical reason for choosing Webots: at project start, a maintained,
  ROS2-Humble-compatible e-puck2 model with working `webots_ros2_driver`
  integration was available and known-working, whereas the standard
  e-puck2 Gazebo plugin stack for ROS2 Humble was not confirmed working in
  this environment; Webots was chosen to keep Objective 1 (environment
  setup) from stalling the schedule.
- **Recommendation**: confirm with the supervisor (Dr. Arshad Jhumka)
  whether Webots is an acceptable equivalent simulator for the Spec's
  stated Gazebo requirement, and if so, get that agreement in writing
  (email or supervision-meeting note) to cite in the dissertation's scope
