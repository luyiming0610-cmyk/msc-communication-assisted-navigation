# Root-cause audit: dynamic-heading / local-avoidance interaction (2026-07-20)

Read-only audit only. No code modified, no pilot run. Covers
`shared_exit_n2_n2_exit_comm_off_EXCLUSIONARY_PILOT02` and `_PILOT03`'s
already-recorded bags and logs.

## 0. Correction of prior report

My earlier report attributed PILOT03's `DURATION_CEILING` failsafe to
"Robot B's encounter with the pre-registered obstacle." That is wrong.
The failsafe latched on **Robot A**, well after Robot A had already
individually reached the goal. See Section 3. `PILOT02_analysis/NOTE.md`
and `PILOT03_analysis/NOTE.md` both carry a REVISION NOTE recording this
correction; the original text is preserved beneath it, not deleted.

## 2. `desired_heading` behavior at/near zero distance (confirmed by source, not just data)

`navigation_target_state.py`'s `NavigationTargetState.desired_heading_rad()`:

```python
def desired_heading_rad(self, x_m, y_m):
    tx, ty = self.current_target
    return math.atan2(ty - y_m, tx - x_m)
```

Computed **unconditionally every tick** (`goal_navigator.py`'s `_tick()`,
2Hz), with **no distance check, no arrival state, no hold logic**. As
`(x,y) -> (tx,ty)`, `atan2`'s result becomes maximally sensitive to
sub-millimeter position noise -- a textbook go-to-goal singularity. The
observed continuous yaw-spin with a position frozen at the target is the
direct behavioral signature of this.

## 3. Does a robot keep receiving nonzero navigation input after individually completing?

**Yes, confirmed by both source and data.** `goal_navigator.py`'s
"informed" mode target is set once at construction and never changes;
its 2Hz timer keeps publishing a freshly-computed `NavigationIntent`
forever, regardless of whether the robot has entered/held the goal
region. Nothing in this study's current design ever tells an
individually-arrived robot to stop:

- `cooperative_avoider.py`'s own `_complete()`/`stop_after_recovery`
  mechanism is about recovering from a CPA/local-avoidance encounter,
  unrelated to "reached the navigation target."
- `task_completion_monitor.py` only ever signals `TASK_COMPLETE_GOAL`
  once **both** robots simultaneously satisfy the hold criterion -- it
  has no notion of, and does not publish, an individual robot's
  arrival, and even if it did, nothing currently subscribes to it.

This is confirmed as the dominant root cause of Robot A's failsafe in
PILOT03 and its matching (sub-ceiling) behavior in PILOT02.

## 4. Real sensor readings at the LOCAL trigger (both robots, verified via `dump_state_sensor_trace.py`)

| | Distance closing pattern | left/right | Interpretation |
|---|---|---|---|
| Robot A, PILOT03, `t=33.7-40.0` | oscillates 0.17-0.31m in step with yaw spin, position fixed | `inf` throughout | Sensor cone sweeping past a nearby structure (gate posts) during an unstable in-place spin, not a single static obstruction being approached |
| Robot B, PILOT02, `t=31.6-33.5` | monotonically closes 0.92m -> 0.18m as robot turns toward waypoint 1 | `inf` throughout | Genuine, real detection of the pre-registered obstacle |

Both are **real sensor readings**, not `inf`-while-still-triggering
artifacts -- the local-avoidance state machine itself is not
misbehaving; it is correctly, cautiously responding to what its sensor
genuinely reports in both cases. The obstacle explains Robot B's first
encounter; it does not explain Robot A's failsafe at all.

## 5. Proven root cause (summary)

**Two design gaps in the new `goal_navigator`/dynamic-heading layer,
NOT in the frozen local-avoidance state machine (confirmed unchanged,
still purely sensor-driven, no coupling to heading whatsoever --
`local_obstacle_logic.py` was read in full for this audit):**

1. **No arrival/hold state**: `desired_heading_rad()` has no
   distance-to-target special case, so it keeps computing an
   increasingly noise-sensitive heading forever as a robot's position
   converges on its target.
2. **No individual-completion lock**: nothing stops an individually-
   arrived robot's navigation input, because the system's only
   "done" signal (`task_completion_monitor`'s all-robots check) is
   external, all-or-nothing, and not wired back to either robot's own
   navigator.

Together: an informed-mode robot arrives, keeps being driven by an
increasingly unstable heading command, spins in place, and this spin
can (and in PILOT03, did) consume enough of the local-avoidance state
machine's 25s encounter budget to trip its own, correctly-functioning,
unmodified safety ceiling. The pre-registered obstacle is a real,
independent contributor to Robot B's separate difficulty, not a cause
of Robot A's failsafe, and not the dominant explanation for either
robot's overall pattern.

## 6. Minimal fix design (goal_navigator / NavigationIntent layer only -- proposed, NOT implemented)

Per instruction: does not touch `local_obstacle_logic.py`,
`decide_local_obstacle()`, `EncounterAvoidanceV4`, any IR/ToF threshold,
`DURATION_CEILING`, or CPA/safety-radius parameters. The existing
circular goal-region + hold-time criterion already matches the
"enter the exit's safe zone and hold briefly" semantic -- no change to
that judgment geometry is proposed.

**`NavigationIntent.msg` (revise before any formal use; PROTOCOL_
VERSION=1 stays as the technical version field, not renamed):**

```
uint32 PROTOCOL_VERSION=1

uint32 protocol_version
uint32 source_robot_id
uint32 sequence
builtin_interfaces/Time production_stamp
float64 desired_heading_rad
float64 desired_linear_speed_mps
string navigation_phase   # "SEARCH" | "GO_TO_EXIT" | "ARRIVED_HOLD"
bool valid
```

**`navigation_target_state.py` / `goal_navigator.py`:**

- `goal_navigator` gains its own, self-contained arrival detector,
  reusing the existing, already-tested `GoalHoldTracker`
  (`goal_hold_tracker.py`) with the SAME frozen goal center/radius/
  hold-time it is already given -- no new dependency on
  `task_completion_monitor`, no cross-process coupling.
- On arrival (hold satisfied), `navigation_phase` switches to
  `ARRIVED_HOLD`: `desired_linear_speed_mps=0.0`, and heading
  computation freezes (publishes the last pre-arrival heading, or holds
  the last commanded value) rather than continuing to recompute
  `atan2` at near-zero distance.
- Before arrival: `navigation_phase="SEARCH"` (Robot B, pre-switch) or
  `"GO_TO_EXIT"` (Robot A always; Robot B post-switch under COMM_ON),
  `desired_linear_speed_mps` set to the pre-registered
  `nominal_speed_mps`.
- Waypoint advancement stays exactly as-is (already confirmed
  monotonic, no fix needed there).

**`cooperative_avoider.py` (flagged for explicit confirmation before
any implementation -- this is the second touch to this file after the
`enable_dynamic_heading` addition):**

- A new, symmetric, default-disabled `enable_dynamic_speed` parameter
  mirrors `enable_dynamic_heading` exactly: when off (default, and
  every prior study's configuration), CRUISE keeps using the fixed
  `nominal_speed_mps` exactly as today. When on, CRUISE's linear
  command is driven by `NavigationIntent.desired_linear_speed_mps`
  (with the same freshness-check-and-fallback-to-`nominal_speed_mps`
  pattern already implemented for heading) -- this is the only way an
  `ARRIVED_HOLD` robot can be commanded to a genuine zero linear speed,
  since CRUISE currently always applies the fixed nominal speed
  regardless of any dynamic heading input.
- CPA avoidance, local IR/ToF safety-stop, and stale-state handling
  remain unaffected and strictly higher priority, exactly as the
  existing `enable_dynamic_heading` addition already guarantees.

**Parking-slot contingency (addressing double-occupancy of a single
goal point once Robot B can also arrive):** since Robot A's informed
target and Robot B's eventual (COMM_ON) announced target are currently
the identical point (0.5,0.5), two robots successfully arriving would
be commanded to the same coordinate. Proposed: two small, frozen,
non-colliding hold offsets within the same goal region (e.g.
±0.05m along a perpendicular axis from the shared exit point) -- the
shared exit/goal identity and judgment region are unchanged; the offset
only affects each robot's own final parking point once individually
arrived. Not yet designed in detail; flagged for confirmation together
with the rest of this fix before implementation.

## 8. Not done, per instruction

No code modified. No pilot run. Obstacle left exactly where it was --
